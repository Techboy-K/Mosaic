## Where authorization lives
In Postgres, not in the browser. Every table has Row Level Security; every policy resolves
through `has_perm()`, `auth_level()` and `outranks()`. Hiding a button changes nothing —
the same rules apply to a hand-written API call.

Three guarantees are enforced by database triggers rather than application code:

1. **System owners are permanent.** Cannot be deleted, disabled or demoted, by anyone,
   including another owner.
2. **Nobody can grant a role at or above their own authority.** An Admin cannot create
   an Admin. Peers cannot act on peers.
3. **Order status only changes through `transition_order()`.** A direct `UPDATE` on the
   column is refused.

The audit log has `UPDATE` and `DELETE` revoked from every application role. It cannot be
rewritten, by a superadmin or anyone else.

## Roles as shipped

| Role | Level | Sees |
|---|---|---|
| Superadmin | 0 | Everything, plus roles and settings |
| Admin | 10 | Both branches, staff, menu, orders, reports, audit |
| Supervisor | 20 | Command centre, all orders, history |
| Chef | 30 | Kitchen queue only |
| Waiter | 40 | Their orders, new order, quick notes |

Levels are data. A superadmin can add a role at any level through **Roles → Create role**;
navigation updates for everyone holding it, with no deploy.

## Order lifecycle
```
DRAFT → SUBMITTED → SENT_TO_KITCHEN → IN_PREPARATION → READY → SERVED → COMPLETED
                              ↕                ↕          ↕
                        NEEDS_ATTENTION   (supervisor may enter any state)
```
Each state names the role that owns it. When an order moves to a state owned by a different
role, it leaves the previous queue and appears in the new one.

**The 30-second undo is server-side.** `order_events.undo_expires_at` is set by Postgres and
checked by Postgres. The countdown in the browser is decoration; changing the system clock
achieves nothing. Only the person who made the change can undo it — or a supervisor.

## Adding staff
**Staff → Add staff.** Six steps. Only roles below your own authority are offered, and the
server checks again when you submit.

Two onboarding routes: an emailed invite (they set their own password — preferred), or a
temporary password for kitchen staff without email, flagged to force a change at first login.

## Menu
**Menu** is the operational source of truth and drives the waiter's order screen immediately.
The public website keeps its own static `data/menu.json`, so it stays up even if the database
does not. **Publish to website** exports a fresh `menu.json` to drop into `website/data/`.

## Sound
Browsers block audio until someone interacts. The kitchen and order screens show a one-time
**Enable sound** prompt. Volume and on/off live in Settings.
